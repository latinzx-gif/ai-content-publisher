# SOP-002: Hermes Morning Brief

- **ID:** SOP-002
- **Version:** 2.0
- **Status:** Active
- **Owner:** Hermes Agent
- **Schedule:** Every day at 06:00 Asia/Bangkok (UTC+7)
- **Delivery:** Telegram message → user approval → TODAY_AGENT_TASK.md

---

## 1. Purpose

To generate a concise daily briefing that reads the current HEAD-OFFICE state, selects the first P1 cashflow task from `NEXT_GEMINI_TASKS.md`, and produces a scope-limited Codex prompt for immediate execution. The prompt is only materialized as `TODAY_AGENT_TASK.md` after the user explicitly replies **APPROVE** in Telegram.

**Fast: No LLM call.** The brief is generated by shell script directly. No inference latency. No timeouts. No fallback needed.

This approval gate prevents premature task creation and lets the user hold or redirect effort each morning.

## 2. Input Sources

Lightweight context — only the minimum needed to pick a task:

| File | Purpose | Always? |
|------|---------|---------|
| `HEAD_OFFICE_CURRENT_STATE.md` | Current phase, completed work, blockers, warnings | Always |
| `NEXT_GEMINI_TASKS.md` | Pre-defined executable tasks with exact prompts | Always |
| `STRATEGIC_PRIORITIES.md` | P1–P4 priority definitions | Only if < 200 lines |

Excluded (too large / not needed for brief):
- `HEAD_OFFICE_ACTIVATION_PLAN.md`
- `HERMES-BRAIN/SOP/KNOWLEDGE_LIFECYCLE.md`

## 3. Task Selection Priority

Tasks are selected by **keyword scoring** — not by position in the file. Every task in `NEXT_GEMINI_TASKS.md` is parsed, scored, and the highest-priority task is chosen.

### Priority Levels (lower score = higher priority)

| Score | Level | Keywords |
|-------|-------|----------|
| **1** | **P1 Cashflow** | AI Content Publisher, client delivery, delivery readiness, handoff, QA, Buffer, image generation, creative approval, Supabase storage, image metadata, metadata db, image validation, batch upload, upload, storage, gallery, media |
| **2** | **P2 FASTWORK** | FASTWORK, service package, pricing, sales asset, requirement form, support scope |
| **3** | **P3 DATACLAW** | DATACLAW, market scan, signal, dataset, report, research pipeline |
| **4** | **P4 INVESTMENT** | INVESTMENT, risk policy, drawdown, capital preservation |
| **5** | **P5 System** | HERMES, system, documentation, cleanup, architecture |

### Scoring rules

1. Each task's name + description + steps are merged into a single lowercase string.
2. Keywords are matched as regex alternations (e.g. `ai content publisher|client delivery|...`).
3. The **lowest score** wins (P1 > P2 > P3 > P4 > P5).
4. **Tiebreaker:** the earlier task in the file wins.
5. If **no keywords match** (score 99), the task is deprioritised — only used if nothing else matches.
6. If **no tasks exist at all**, the safe default is:
   `"Validate AI Content Publisher delivery readiness"`

## 4. Impact Classification

For the chosen task, classify across four dimensions:

| Dimension | HIGH | MEDIUM | LOW |
|-----------|------|--------|-----|
| **Cashflow** | Direct billable revenue today | Revenue within 1 week | No direct revenue |
| **Asset** | Creates a sellable/durable asset | Creates a component of an asset | No asset created |
| **Risk** | Prevents a likely loss or blocker | Reduces moderate risk | Minimal risk impact |
| **System** | Enables other OS workflows to run | Improves one workflow touchpoint | Documentation only |

## 5. Approval Workflow

```
┌──────────────────────────────────────────────────┐
│  Phase 1 — Generate (06:00 automated)             │
│  hermes_morning_brief.sh                          │
│  ├─ Reads CURRENT_STATE.md + NEXT_GEMINI_TASKS.md │
│  ├─ Picks highest-priority P1 task by keyword     │
│  ├─ runtime/latest_morning_brief.md  (Telegram)   │
│  └─ runtime/pending_agent_task.md   (Codex)       │
└──────────────────────┬───────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────┐
│  Phase 2 — First Approval (user-driven)           │
│  check_telegram_approval.sh                       │
│                                                   │
│  APPROVE → cp pending→TODAY_AGENT_TASK.md         │
│  HOLD    → nothing                                │
│  CHANGE  → revise manually                        │
└──────────────────────┬───────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────┐
│  Phase 3 — Execute (user-driven)                  │
│  User runs: codex exec - < TODAY_AGENT_TASK.md    │
└──────────────────────┬───────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────┐
│  Phase 4 — Complete (user-driven)                 │
│  complete_current_task.sh                         │
│  ├─ Reads TODAY_AGENT_TASK.md (completed task)    │
│  ├─ Checks git status for changed files           │
│  ├─ Picks next task (skips completed one)          │
│  ├─ runtime/latest_task_completion_report.md      │
│  ├─ runtime/next_pending_agent_task.md            │
│  └─ Sends Telegram with completion + next task    │
└──────────────────────┬───────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────┐
│  Phase 5 — Next Approval (user-driven)            │
│  check_next_task_approval.sh                      │
│                                                   │
│  APPROVE_NEXT → cp next→TODAY_AGENT_TASK.md       │
│  HOLD         → nothing                           │
│  CHANGE       → revise manually                   │
└──────────────────────────────────────────────────┘
```

### Step-by-step

**Phase 1 – Generate (06:00, automated)**
1. `hermes_morning_brief.sh` reads all input sources.
2. The Hermes agent selects exactly one P1 task using the priority rules.
3. The agent generates two outputs:
   - Formatted Telegram message → `runtime/latest_morning_brief.md`
   - Scope-limited Codex prompt → `runtime/pending_agent_task.md`
4. The script sends `latest_morning_brief.md` to Telegram.
5. **`TODAY_AGENT_TASK.md` is NOT created yet.**

**Phase 2 – Approval (user-driven)**
1. User reads the Telegram brief.
2. User replies with one of: `APPROVE`, `HOLD`, `CHANGE`.
3. `scripts/check_telegram_approval.sh` fetches the latest Telegram message and checks the reply.

**Phase 3 – Resolution (on APPROVE)**
1. `check_telegram_approval.sh` copies `runtime/pending_agent_task.md` → `HEAD-OFFICE/TODAY_AGENT_TASK.md`.
2. Sends Telegram confirmation: "APPROVED. TODAY_AGENT_TASK.md created. Run: codex run TODAY_AGENT_TASK.md"

**Phase 3 – Resolution (on HOLD)**
1. No task file is created.
2. Sends Telegram confirmation: "HELD. No task created."

**Phase 3 – Resolution (on CHANGE)**
1. No task file is created.
2. Sends Telegram confirmation: "CHANGE requested. Please revise task manually."

## 7. Security Rules

- **TELEGRAM_BOT_TOKEN** and **TELEGRAM_CHAT_ID** must never be hardcoded in scripts.
- Load secrets from environment variables or a `.env` file sourced at runtime.
- Never print secrets to stdout, logs, or saved files.
- The `.env` file must be excluded from any version control.
